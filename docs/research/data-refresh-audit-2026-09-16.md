# 数据刷新慢、失败与手动依赖：专项诊断

日期：2026-09-16。Issue #499。源码基线：`ae681c1`。本轮完成诊断与离线复现，未改动生产数据、应用设置或刷新实现。

## 判断

问题确实存在，而且横跨任务呈现、刷新规划、执行调度、数据契约和应用交付。不能把它们统一解释成网络不稳定，也不能靠加一个定时器或提高并发解决。

应优先修复“排队任务不再跟踪、失败结果被当作完成”和“重复执行无效刷新”。再完善后台按缺口补齐，使用户查看数据时通常无需主动维护数据。

## 证据范围

- 只读检查实际安装实例的健康响应、配置、日志和 SQLite 任务/结果记录；未触发全市场下载。
- 实际应用健康响应的构建为 `7c4d253`；当前源码已经是 `ae681c1`。合并到 main 不会自动激活安装实例，所以不能把源码中已合并的修复直接视为用户已用到的修复。
- 历史任务时间范围为 2026-07-27 至 2026-09-15，跨多个版本。以下数字是该历史样本的状态和墙钟耗时，包含等待、失败及恢复时间，不是最新版基准或当前实时故障率。
- 2026-09-09 起，非新闻相关的已记录样本仅有一次盘后流水线和一次轮动刷新，均完成；不足以用历史总体失败率描述最近一周。
- 审查中安装实例退出；日志说明启动器退出后应用安全停止。本轮没有启动、停止或替换生产实例。

| 历史任务 | 样本与结果 | 记录的平均/最大耗时 |

## 已确认的问题

### 1. 设置页与后台任务状态脱节

位置：`quantmaster/server/static/settings.js` 的 `renderDataRefresh`、`pollDataRefresh`；`quantmaster/data/maintenance.py` 的 `_handle`、`_project`。

后端提交任务可以返回 `queued`。设置页仅对 `running`、`cancelling` 安排下一次轮询，也仅对这两种状态保留正在跟踪的任务 ID。结果是首次查询还在排队时，页面直接停止跟踪，无法自动看到随后开始执行和完成的状态。

后端有失败项时保留 `status=completed`，同时在结果中记录 `outcome=completed_with_warnings` 和失败数量。设置页却判断旧的 `completed_with_errors` 状态，不使用这个 outcome：它显示“增量同步完成”，隐藏重试按钮，并清除提醒。失败文本仍可能显示在局部区域，因此不是完全丢失错误信息，而是总状态、提醒和可执行操作不一致。

离线执行原始渲染/轮询函数、替换网络和 DOM 后得到：

| 输入 | 当前页面行为 |
| --- | --- |
| queued，0/3 | 下一次轮询数为 0；任务 ID 被清空；提醒被 resolve |
| completed + completed_with_warnings，3/3 失败 | 显示“增量同步完成”；重试按钮隐藏；提醒被 resolve |

这是功能缺陷，不需要慢网络才能复现。应统一使用当前任务契约，区分排队、运行、全部成功、部分失败和全部失败，并测试从排队到完成的整个过程。

### 2. “增量”仍会重复请求已新鲜的数据

位置：`DataRefreshManager._refresh_one`；`registry._load_history_locked`。

数据刷新管理器固定传入 `RefreshMode.INCREMENTAL`。在近七日范围内，这个模式强制刷新尾部重叠区间，并传入 `refresh_provider_cache=True`。它缩小了下载区间，却没有保证“数据无变化时不下载”。

离线构造覆盖完整、检查时间新鲜的缓存，两次相同请求结果：

- AUTO：刷新分段调用 0 次。
- INCREMENTAL：刷新分段调用 2 次；两次都要求绕过提供方缓存。

该探针替换了实际获取函数，证明的是规划层会重复请求，不是某个真实源的网络耗时。普通自动刷新应由缺口和数据代际决定是否执行；强制校正尾部应保留为明确的操作，而不是每次默认行为。

`DataRefreshManager.create` 也没有提供业务键、输入指纹和算法版本，统一任务账本只能合并仍活跃的同规格请求，不能复用已经完成的同代际结果。多个不重叠的触发可能反复执行同一轮工作。

### 3. 固定批次让慢标的阻塞后续任务和进度保存

位置：`DataRefreshManager._handle`。

每批最多 8 个标的；虽然批内并行，但必须等整批 Future 返回，才更新成功/失败、写检查点、推进下一批。一个慢标的会让其余已经完成的结果无法及时显示和持久化，也会让空闲执行槽无法服务下一批。

离线把并发设为 2，令 A 等待事件、B 立即完成、C 尚未执行：B 完成后，C 仍未开始，检查点数仍为 0；释放 A 后才继续。这里使用事件控制依赖关系，不把模拟等待时间当作生产提速测量。

取消检查也在批次前后，`ThreadPoolExecutor` 上下文会等待批内任务退出。应改为有界的持续补位调度，逐标的持久化完成状态，并明确取消后不再派发新任务、在途调用按截止时间退出的边界。

### 4. 部分“刷新失败”实际是无法靠下载修复的契约缺口

七次市场刷新结果来自 2026-08-16、08-17、08-28，每次都是 29 项全部未通过。典型类别包括单位证据、交易日历、连续合约映射以及复权证据；同一标的可以有多个类别，计数不能相加。

以其中一次为例：18 项包含 `MARKET_SESSION_UNSUPPORTED`，7 项包含 `continuous_contract_unconfirmed`，27 项涉及单位证据。

管理器将所有非 verified 结果转换成失败字符串，最后仍返回“任务完成”。虽然服务端 resume 可以只重试失败项，但它不区分可重试网络错误和确定性的契约缺失；`max_attempts=8` 也不会自动修复一个已经返回 completed 的任务。

不能通过放宽 verified 门槛解决。应在执行前辨别支持范围，执行后分别报告：是否拿到新数据、是否满足展示用途、是否满足正式研究、缺口是否能自动修复。单位/日历/连续合约等缺失应指向对应适配器或证据修复，避免让用户无限点击同一个按钮。

### 5. 自动更新存在，但没有覆盖所有消费数据

位置：`free_stockdb_runtime._scheduler`、`StockDBEventDispatcher.deliver`、`DataRefreshManager.start`、`registry.read_history`。

实际配置启用了 StockDB 自动更新、15:50 检查、盘后自动运行和数据修复。不能归因于“用户没开自动刷新”。

现有主链路是 StockDB 调度检查目标交易日，成功/部分会话事件再触发市场参考行情和轮动等下游。`DataRefreshManager.start` 主要恢复任务执行，不会自行遍历所有消费范围；其直接自动创建路径是 `scope=market`，不是所有候选、缓存和研究证据的统一维护。

`read_history` 是严格的只读缓存入口，缺失或过期时返回带状态的数据，不会提交刷新。这个读取边界应保留。但 `stale_while_revalidate` 元数据本身不是后台刷新动作，仍需要工作进程在启动、交易日切换和订阅范围变化时接纳对应的去重刷新任务。

因此应按实际消费范围维护数据：市场参考、用户关注范围、候选及研究依赖分别规划，复用同一份本地 StockDB 和缓存。不要让每个页面自行发起全量维护，也不要默认对全部历史缓存持续下载。

### 6. 实际运行版本和外部来源变化会抵消源码修复

安装实例日志在 2026-09-15 仍反复请求旧 StockDB 公告地址并收到 HTTP 451。源码的官方域名/SDK 适配已由 PR #498 合并，但观测到的运行构建更旧，尚未包含它。

这能确认外部通知查询存在失败和部署版本差异，不能仅凭该日志断言所有行情下载都失败。应先在明确构建上验证通知、StockDB 本地服务、目标交易日和下游发布，再归因于当前代码。完整新构建的激活与源码合并分开记录；本轮未执行激活。

## 修复顺序与验收

| 顺序 | 工作 | 验收标准 |
| --- | --- | --- |
| 1 | 修正设置页任务状态和结果呈现 | queued 持续跟踪；部分/全部失败可见；可重试时按钮可用；退出页面停止轮询 |
| 2 | 统一普通刷新规划、去重与失败分类 | 同数据代际重复触发为零远程调用；只补缺失/陈旧字段；确定性契约错误不自动重试 |
| 3 | 去除批次阻塞，细化检查点和取消 | 慢 A 不阻塞其他可运行标的；完成项立即持久化；恢复不重跑已成功项 |
| 4 | 补齐后台维护覆盖与来源适配 | 在工作进程中按消费范围自动接纳缺口；StockDB 优先；数据已就绪才触发依赖计算 |
| 5 | 用实际安装构建做端到端验收 | 分别记录排队、读取本地、远程补齐、计算和发布耗时；核对版本及输入交易日 |

性能目标应按场景设定：已有可用快照的页面读取不等待网络；输入未变的刷新不调用远端；缺口刷新记录实际网络次数和等待原因；冷启动全量准备单独显示规模与预算。不能承诺所有研究任务都在几秒完成。

## 复现与限制

本任务保留 `refresh_probes.py` 和 `settings_refresh_probe.cjs` 两份本地离线探针：前者执行当前 Python 刷新循环与缓存分段规划，后者执行当前设置页函数并替换网络/DOM。没有下载市场数据、伪造正式证据或修改真实账户。

页面探针不是完整浏览器端到端测试；后续 UI 修复仍需验证真实页面。历史数据库统计没有证明最新版仍会出现旧子进程故障，也没有把旧数据批量重算。以上诊断用于确定修复边界，不能当作已经修复或已经实现生产提速的声明。
